# 现场演示脚本（2 分 40 秒）

## 演示前

- 使用 Chrome 或 Safari。
- 启动 `python3 -m audiobook_app`。
- 新开无痕窗口走一遍完整路径。
- 若演示真实百炼，提前确认余额、Key、Workspace ID 和网络。
- 准备离线模式作为备用；不要把缓存结果说成实时生成。

## 0:00–0:20 · 痛点

讲：

> 现在很多听书产品已经能把文字念得很像真人，但旁白、少女、老人和小孩仍可能共享一条声线。问题不只是 TTS 自不自然，而是系统根本没有先理解“谁在说话”。

操作：停留在首屏，指向“小说不该只有一个声音”。

## 0:20–0:45 · 输入

操作：

1. 指出可以拖入 UTF-8 / UTF-16 / GB18030 TXT，再点击“载入原创演示文本”。
2. 快速滚动文本，指出其中有林夏、陈默、老爷爷和小男孩。
3. 点击“自动识别角色”。

讲：

> 这段文本完全原创，所以演示没有版权问题。普通用户不用选择模型，系统会自动使用当前最合适的识别方式。

## 0:45–1:25 · 角色卡

操作：

1. 展示旁白与人物角色卡。
2. 指出系统判断，并点击一位角色的“试听”。
3. 给一位角色更换声音。
4. 展开“角色信息与别名”，说明复杂能力仍在，但不会挡住普通用户。

讲：

> 用户只需要判断“这个声音合不合适”。年龄、别名、证据和供应商兼容性都由系统管理，需要时才展开。

## 1:25–1:55 · 台词纠错

操作：

1. 滚动到“检查朗读脚本”。
2. 点一条句子的“角色错了”，再选正确人物。
3. 选中一个多音字，点“这个字读错了”，保存全书发音。
4. 指出“重做这句”不会重新生成其他内容。

讲：

> 全自动不可能永远正确，所以产品壁垒不只是识别率，还包括纠错成本。角色改动只影响本句；人名读音纠正一次，全书都记住。

## 1:55–2:20 · 多人试听

操作：点击“从头试听”，指向当前说话人；切换倍速，再从另一句点击“从这里听”。

讲：

> 这一步完全免费，不需要 API Key。浏览器会按角色使用不同的语速和音高，先让用户判断选角是否合适。

## 2:20–2:40 · 真实生成与收束

优先操作：指出页面只显示句子、字数、已准备内容和预计费用，再点击“开始生成”，确认提示并播放预先控制在 30–45 秒的结果。

断网备用：使用浏览器自然试听；在 Mac 上还可点击“免费生成（Mac）”
生成真实中文朗读。内部测试音已经从用户界面移除，不作为演示内容。

讲：

> 用户不需要理解 TTS、Token、请求数或音频轨道。系统自动管理生成、拼接、复用和失败恢复；未来更换底层语音供应商，也不需要重做角色系统。

结束：

> 我们没有再造一个“更像人的朗读器”。我们给 TTS 补上了它缺失的导演层：先理解人物，再为每个角色选声。

## 答辩准备

### 为什么不用一个 LLM 直接输出整本书音频？

角色归属、人工修改、缓存、费用、失败重试和供应商替换都需要中间结构。直接一次生成不可解释，也无法只重做错误片段。

### 为什么还需要人工纠错？

小说常省略主语、使用别名和自由间接引语。承认不确定并让人快速修正，比强行猜错更像可用产品。

### 用户是否必须买 Token？

正式消费产品默认由平台统一付费，用户买应用积分；BYOK 只作为高级选项。课堂 MVP 由团队在服务端配置受限 Key。

### Qoder 帮了什么？

按真实记录回答：需求拆解、数据合同、代码骨架、规则测试、错误定位、README 和演示脚本。展示 Prompt 迭代，不要只说“让它写了代码”。
